# 产品上下文：公屏文字回复、进场欢迎与礼物感谢

## 需求与来源

Requirement ID `REQ-011`，已由原主线程经 lifecycle CLI 登记并绑定 `FEAT-008`；进度以 state 投影为准。源需求为 [REQ-004.product.md](REQ-004.product.md) 中 NEED-003、DEC-001、故事 2/3。原 REQ-004 保持 captured，登记、私信、挂载和 Robot 消费不由本增量交付。

已确认来源：2026-11-13 用户要求新线程完成公屏回复、欢迎、感谢；当前任务明确授权普通本地实现及必要验证，并要求现有 Drawer、默认关闭、可信固定账号/房间、保护匿名输入和原结果未知时禁止重发。长期产品方向文档为 none；不虚构额外目标。

### 已确认规则

- 主人在现有直播设置 Drawer 配置发送能力，保存配置不登录、不连接发送账号、不发送、不探测真实服务、不开播。发送默认关闭；手动、Agent 回复、欢迎、感谢分别有明确开关/状态。仅真实 owner 可修改、授权、发送和核对原操作。
- 发送使用独立受控的登录账号和发送实例，房间来自已保存的当前抖音房间。DyHub本地账号记录与真实抖音主体是不同实体；只有从实际发送认证上下文（冻结HTTP材料）核出的真实主体字符串ID与可信预期相符才可授权。主体未知、Cookie/登录状态改变或重新登录均废弃旧资格。模型与观众输入不能指定账号、房间、URL、角色或授权。现有匿名采集目录、只读 LiveSource、原 TTS/舞台、B 站路径保持职责。
- 复用已有事件及 Agent，不将每段助手正文自动复制到公屏。Agent 仅对当前真实公屏事件发一条明确回复；欢迎/感谢用非敏感短模板，按原事件来源校验、合并和节流。模拟事件不可触发真实发送。礼物金额 unknown，连击使用输入增量，不根据累计数重复感谢。
- 所有文字是普通公开内容：不读取/拼接登记Base、联系方式、照片/附件或资料记录，拒绝可识别的联系方式和链接/附件语法，不宣称私信、挂载或登记成功。校验不能识别任意语义隐私，owner/Agent仍只可提供普通非敏感文字；不将语法校验描述成完整隐私识别。欢迎模板不回显未经处理的观众名字；礼物感谢不推断金额。
- 队列有界、单在途、有限速/过期；重复请求返回原操作，不重复派发。目标、直播会话/epoch、输入或发送连接代次、主体或授权变更使旧队列失效；发送端各异步阶段及每次应用HTTP写入前仍核原绑定。调用实际应用数据写入开始即可能产生不可撤回副作用，不能以零返回字节或异常认定未执行。重连或重启不恢复授权、不重放旧队列。
- 区分未派发、排队、派发中、明确未执行、HTTP请求/接口返回状态、结果未知；接口返回成功码/同文 echoed 不证明平台受理或观众可见，不能当平台投递回执。原结果未知时暂停发送并保留原请求，禁止新 ID、重启、换 API/UI 或换目标掩盖原结果。真实owner只能提交绑定原请求/主体/房间的核对事实：未看到不是未发送证明，备注不结算unknown。明确未执行须有原执行已终止且从未调用实际应用HTTP写入的可信终态依据；有归属的正面观察另记人工观察，不能写成not_sent或平台receipt。仍活着的原执行始终占用单在途；本增量没有“承担风险后直接解除unknown”入口。原请求及其原事件不重发。
- 自动回复/欢迎/感谢须同时有当前匿名输入的进程内原事件关联、当前输入连接代次，以及受控sender直接从原始平台消息取得的新鲜度证明。缺失/回退为本地now/旧时间/类型或rawId不匹配均不可自动外发；不从昵称、文本或普通输入字段自报推断来源。真实gift接收能力单独保持未验证。
- API 优先。直播伴侣只保留明确不可用的备用状态和手动验证说明；本增量不实现未经验证的 UI 自动发送。没有安全可用 API 时显示不可用；unknown 时 UI 也不可重发。

## 详细规格

### 用户故事与验收场景

1. 给定无发送装配或未授权，主人打开原 Drawer 并保存设置，则明确显示未装配/未验证/未授权、保存结果及生效草稿；没有网络发送、登录、连接或开播副作用。
2. 给定独立实例、可信已登录账号、当前抖音房间及连接均核对有效，主人显式启用并授权后发送一条普通文字，则仅向该固定目标派发一次；控制台保留原请求、渠道和真实结果层级。可见须由另一观众核对。
3. 给定非 owner、模型给任意目标、过期授权、B 站目标、模拟输入或资格不成立，尝试授权/发送，则拒绝且零外发，不更改匿名采集保护。
4. 给定真实公屏事件及原 Agent 当前回合，Agent 选择公开回复，则原事件/会话有效时最多派发一条；助手普通正文不自动镜像到公屏，重放工具不重复发送，旧回合不借新授权发送。
5. 给定真实进场或 gift 事件且对应开关已开，输入重复、同用户短时重复进场或礼物连击增量，则输出有限短欢迎/感谢，重复不刷屏、不把 unknown 金额写成 0 元、不把累计数当增量重复计入。
6. 给定排队期间目标切换、撤权、下播、输入或发送端断连，旧队列失效且不晚发；派发后的迟到响应只更新原操作，不重新启用当前发送，不覆盖新目标状态。
7. 给定接口在派发前明确拒绝，显示有证据的未执行及恢复条件；给定发送请求可能已到达、响应丢失/超时或服务重启，保留 unknown 并暂停自动/手动新发送。重存配置、重启、新请求 ID 均不能绕过。
8. 给定未知操作待核对，主人看到原引用及核对入口；任意备注/未看到消息不能结算unknown。可信原操作终止收据证明从未调用实际应用HTTP写入时可记明确未执行；正面人工观察须关联原主体/房间/时间/内容摘要，并与执行终止事实分开保存，不伪称平台确认。无终止证明/证据冲突时保持暂停；原请求不重新执行。
9. 给定文本含联系方式、照片、附件或资料记录链接，拒绝公开发送；欢迎/感谢中的昵称和礼物名不能通过换行/URL/提示词注入生成私密资料输出。
10. 给定控制台375px/1440px、键盘操作、加载/失败/unknown状态，标签、按钮和恢复说明可达，沿 dl-* 组件；失败保留草稿，状态变化可被辅助技术读取。

### 功能需求与实体

FR-1：现有 Drawer 的 owner 设置、显式授权、手动文字发送及分项反馈（场景1–3、8、10）。FR-2：当前公开事件的 Agent 回复与模板欢迎/感谢（场景4–5、9）。FR-3：固定绑定、撤权/排队/重复/unknown/恢复（场景2–8）。FR-4：匿名输入、既有声音/舞台兼容与资料私密（场景1、3、9）。

实体：发送绑定（部署实例、可信账号、固定房间、发送端会话、直播epoch与授权代）；原操作（稳定请求引用、来源事件/回合、目标快照、状态与核对事实）；设置草稿及已保存设置。持久化只保留最小操作元数据及文本摘要，不保存凭据或登记资料；发送授权仅存内存。

### 成功标准

离线真实 HTTP/WS fixture 和宿主接线能证明场景1–10的可执行边界，非 owner/撤权/旧队列/重复轨迹零额外请求；配置保存零外部副作用；自有构建通过且保护的 lib/lib.previous 字节未变。仅离线通过不声明真实抖音发送或匿名真实gift接收通过。

真实验收条件单列：用户核对发送账号/房间、有限内容与次数后，通过安全登录流程发送一条普通文字，另一观众观察；当前尚未具备，标 NOT_RUN。无 commit/push/发布授权，不以当前 HEAD 冒充 WIP 验证版本。

### 范围外、假设与依赖

私信、观众管理、登记挂载/填写、Robot、课程、推流/开播及直播伴侣自动化不在范围。API 为受控HTTP发送器调用非官方网页接口，不是官方开放 API。复用固定接口/纯算法，DyHub固定版本仅提供只读raw来源，必要适配只在固定提交导出的受控副本，不改有他人 WIP 的 D。发送实例与匿名输入分离。登录和平台资格是运行前提，缺失时不可用；不阻止离线代码交付，不声称真实外部验收。

## 发布后观察计划

基线：真实发送/观众可见/匿名gift接收均未验证。候选观察窗口为首次获准的一次手动发送及一次显式恢复；执行者为直播维护者，观众核对者由真实验证时指定。分别记录HTTP写入/接口返回成功码、unknown、另一观众观察、拒绝/重复和错目标轨迹。问题回本增量；登记/私信仍回 REQ-004。当前未发布，不启动观察任务。
