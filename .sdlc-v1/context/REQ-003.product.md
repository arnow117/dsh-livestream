### 需求

#### NEED-001：一个页面选择平台并管理直播间

- **状态**：`confirmed`（用户目标）。
- **陈述**：主人在现有 DSH「直播」页面选择 B 站或抖音、配置对应房间，并完成常用连接、状态查看、恢复与停止，无需在两个控制台间往返。
- **问题与期望结果**：当前平台/房间控件藏在设置 Drawer，抖音采集停止和恢复要求转到独立 DyHub 页面；用户预期它们属于同一个直播间控制台。
- **用户证据**：“为什么抖音的控制台没有merge在直播间控制台内部而是一个单独页面？我预期是合并进去，看看如何处理。一个页面可以配置b站或抖音直播间，看看调整下。完成后再让我来验收”。

### 约束

#### CON-001：复用既有平台与声音能力

- **状态**：`confirmed`（主 Agent 给定边界与 REQ-001/002 已发布行为）。
- **陈述**：保持普通 B 站连接、既有账号/OBS 与下播行为；本地彩排对 B 站真实接入/推流的既有限制继续有效，并在页面清楚提示。抖音仍是匿名只读输入、本地舞台输出，不增加账号登录、Cookie、对外发言或抖音推流。GLM、现有本地 yovoice、声音热更新和私有试听保持原有语义。
- **来源**：主 Agent 的 settled scope；`.sdlc-v1/context/REQ-001.product.md`、`REQ-002.product.md` 的仍有效兼容边界。

#### CON-002：保留目标隔离与有限验证边界

- **状态**：`confirmed`（主 Agent 给定边界与用户既有决定）。
- **陈述**：平台/房间不得在舞台活动、未断开的连接、在途操作或相关清理未完成时改变。测试使用临时配置与注入 fixture，不写真实运行配置，不访问真实房间、模型或 TTS；本轮预算均为 0。完整键盘旅程依用户既有“先交付可用版本，键盘流程后续处理”决定暂缓，不重开该段诊断，不重置既有两次失败及已耗尽的唯一诊断额度。

### 决定

#### DEC-001：原生直播主页承载统一操作

- **状态**：`confirmed`（主 Agent 给定采用项，来源为 NEED-001 的有界实现委托）。
- **采用项**：平台、对应房间草稿、保存、连接状态与恢复/停止操作在直播主页显著呈现；声音及现有高级设置继续留在 Drawer。复用现有 React / `dl-*` 控件、视觉层级和品牌，不嵌入 DyHub iframe，不制作独立管理平台。
- **体验方向**：Operate，按“选择目标 → 保存 → 显式连接 → 查看状态 → 恢复或停止”排列。加载、空态、离线、拒绝访问与错误提供可见且可恢复反馈；不要求用户先理解采集器内部实现。
- **原型决定**：本次复用已确认的原生控制台与明确场景，属于既有 surface 的有界扩展，无需另建候选原型。主 Agent 已加载 Impeccable incumbent context；本阶段未运行原型或生产页面，视觉和交互效果仍须后续正式验证。

#### DEC-002：草稿、已保存目标与活动目标分开

- **状态**：`confirmed`（主 Agent 给定采用项）。
- **采用项**：选平台、输入房间先形成草稿；一次保存提交平台和该平台对应房间，成功后同时生效。未保存草稿不改变活动目标；连接只能使用已保存目标。保存失败不出现半保存状态、不丢草稿；刷新反映最后成功保存的配置。保留另一个平台既存房间、声音和高级设置。

#### DEC-003：同页控制抖音房间，区分订阅与采集

- **状态**：`confirmed`（主 Agent 给定采用项）。
- **采用项**：同页完成匿名房间连接、当前房间采集状态查看、显式重试和停止该房间采集。DyHub 可以继续作为独立后台服务；服务未启动或不可达时，页面如实提示启动依赖并允许重试，不承诺托管进程。新服务如需本地匿名账号记录，可使用空白匿名元数据；不要求访问抖音网站登录或导入 Cookie。
- **状态事实**：服务可达、房间采集中、插件订阅接通与本地舞台运行分别表达。WS 已打开、订阅被接受、健康检查成功、旧快照或启动请求成功都不能单独证明房间 live。
- **停止语义**：“断开订阅”保留只停止本插件接收的兼容行为，并说明采集可能继续；新增“停止该房间采集”是明确的房间级动作，执行前必须说明会影响同房间的其他消费者。它不能停止 DyHub 全局服务或其他房间；失败/部分完成不能显示全部停止成功。
- **恢复语义**：房间 closed/error、离线、断网或超时后不自动重新采集；主人在当前页显式重试，完成必要的当前房间恢复和重新订阅，不再依赖打开独立采集页面。单纯刷新状态不启动采集。
- **不确定结果**：操作超时不证明上游未执行；可能迟到启动时保持“结果未确认”，不能仅凭一次查询未发现房间或停止请求被接受就宣告结束、解锁目标或再次启动。页面说明等待状态核实或人工重启采集服务后的确认方式，不替用户重启共享服务。

### 范围外

#### OUT-001：不扩展平台权限或后台运维

- **状态**：`confirmed`（主 Agent 给定边界）。
- **陈述**：不改 GLM/TTS 或 yovoice 服务，不做 DyHub daemon/进程管理器、自动安装/启动服务、全局停止、远程 bridge 配置、重命名品牌、iframe 集成、新身份/记忆能力、抖音发言/登录/推流、额外 B 站权限或公网发布。独立 DyHub 原生页面可保留为高级排障入口，不能成为普通房间操作的必要步骤。

### 开放问题

- **OPEN-001（外部证据缺口，不阻塞产品规格）**：用户尚未提供可用真实抖音目标房间。确定性 fixture 和本机实际安装的鉴权/空态/离线路径只能证明各自范围，不能证明真实房间事件、礼物、长期稳定性或真实模型/语音联动。本轮不补做真实房间探针。
- 无待用户选择的阻塞产品项；本地匿名元数据、上游状态兼容及并发细节由主 Agent 的只读协议分析确定后进入工程计划，不以猜测替代分析。

### 用户场景与测试 *(必填)*

#### 用户故事 1：在直播主页选择并保存一个目标（优先级：P1）

主人不打开设置 Drawer 即可选择平台、填写对应房间、保存并连接。主入口的价值是降低普通操作在页面间查找的成本。

**独立测试**：在隔离配置上操作真实控制台和真实保存路由，检查前后状态与刷新结果。

**验收场景**：

1. **AC-01**：给定未活动且配置可修改，当进入直播页，则同页可见平台、房间输入、当前已保存/活动目标、保存和连接/断开入口；切换 B 站/抖音草稿即呈现该平台输入要求和权限提示。平台草稿不使标题状态、活动连接或舞台错误地切到另一个目标，且不需要打开独立 DyHub 页面。
2. **AC-02**：给定已保存 B 站 A，另有抖音 B 的草稿，当保存成功再刷新，则平台与 B 同时保留，原 B 站房间与声音/高级配置保留；当校验、持久化或请求失败，则两个生效字段均不改变、草稿保留且能修改重试。未保存/正在保存时不得把草稿当作连接目标；快速重复保存/连接不产生混合目标。
3. **AC-03**：给定抖音目标，当输入合法的数字字符串或完整 `https://live.douyin.com/<数字>` 并保存，则遵循既有输入校验与字符串精度；空白、非法地址等在原页说明原因，不能触发任意 URL 访问。B 站继续遵循原有有效房间输入。切换两个平台不覆盖另一平台已保存房间。

#### 用户故事 2：同页连接抖音并判断失败原因（优先级：P1）

主人显式接入已保存房间，能分清依赖服务、采集、订阅与舞台状态，并在错误后在原页恢复。

**独立测试**：真实控制台/宿主路由/适配器连接专属可控 bridge，分别发送健康、live、connecting、closed/error、拒绝访问与断网结果；真实安装路径的只读空态/鉴权检查单独注明。

**验收场景**：

1. **AC-04**：给定服务健康但房间尚未 live，当点击连接，则展示等待中的房间状态，不能仅因服务健康、WS 打开或订阅接受显示房间已连上；只有目标房间有效 live 确认后，插件才显示接通并可将受控事件交给既有本地舞台路径。状态与事件必须属于当前目标；旧房间的晚到响应不能覆盖新目标。
2. **AC-05**：给定服务离线、空白新服务、房间不存在/未开播、采集错误、权限拒绝或超时，当读取状态或连接，则当前页显示对应失败或未知状态、保留目标并给出下一步；不沿用旧成功状态。健康检查/刷新不开始采集。首次匿名连接需要本地空白账号记录时无需网站登录或 Cookie；依赖不可用时如实提示，不显示接通。
3. **AC-06**：给定一次错误/结束后且先前操作结果已可确认的目标，当主人在同页显式重试，则完成必要的房间级恢复与重新订阅，并按 AC-04 重新等待确认；重试失败仍可在原页继续恢复或停止。后台轮询、传输断开、页面刷新和插件重启均不自动重开采集。重复点击、操作未结束或结果未确认时不产生第二个冲突中的恢复动作。

#### 用户故事 3：明确停止范围并保留已有使用方式（优先级：P1）

主人可选择仅断开本插件或停止当前抖音房间采集，随后安全切换平台；声音和普通 B 站使用不受此次整合影响。

**独立测试**：检查真实路由发出的目标与上游请求、双目标 fixture 的状态、并发失败边界，以及已有声音与普通 B 站回归旅程。

**验收场景**：

1. **AC-07**：给定当前抖音订阅，当选择“断开订阅”，则只清理本插件连接与当前临时上下文，明确采集可能继续；既有断开 API 的调用者保持此语义。当选择“停止该房间采集”，则在执行前显示当前平台/房间并说明影响同房间其他消费者；确认后仅停止此房间并准确反映采集和订阅结果。另一个房间与全局服务保持运行；不会把一次本插件断开显示成上游采集已停止。
2. **AC-08**：给定停止或重试过程中发生网络失败、超时、重复操作或部分成功，当结果返回，则显示可核实的已完成部分及未知/失败部分，保留可恢复入口，不虚报成功；后续确认旧请求的晚到结果不改变另一个目标。特别是超时后上游可能迟到启动时，即使查询暂未发现房间或停止请求被接受，仍显示“结果未确认”并锁定目标，直到可靠状态核实或人工重启采集服务后的确认；A→B→A 的旧操作不能被误认成本次 A 的成功。所有完成反馈与本次房间归属一致。
3. **AC-09**：给定舞台运行、连接中/已连接/错误后保留的连接、在途保存/连接/停止/重试、原有 B 站/OBS 操作或清理，当尝试改目标，则前后端拒绝或禁用并说明先停止、断开或等待的原因，已保存/活动目标不变；操作与清理全部结束后才允许保存新目标。断开及实际目标切换清理旧临时内容，保留声音、B 站历史与已存设置，保持既有下播收尾行为。
4. **AC-10**：给定普通 B 站环境，当在新主入口配置和连接，则保留既有 B 站/OBS 行为，包括等待凭据期间仍能立即断开取消连接；给定本地彩排限制环境，当选 B 站，则页面如实提示该限制，不能出现已真实接入的假成功。抖音路径保持只读/本地舞台语义，不产生 B 站、OBS、网站登录或模型消费副作用。声音 Drawer 的保存热更新、草稿私有试听、错误恢复及原有高级设置继续可用。
5. **AC-11**：给定桌面 1440×900 或窄屏 375×812，当用鼠标完成选择/保存、连接、失败重试、断开和房间级停止，则主要控件与必要警告可读可操作、无横向溢出；加载/空态/错误/忙碌均有反馈，错误信息可帮助恢复。已有 Enter 保存和可见焦点子集保持，不声称完整键盘旅程通过。根 README 与抖音操作说明指向当前同页旅程，并写明后台服务依赖和未验证范围。

#### 边界情况

空配置、平台草稿与活动平台不同、保存失败/返回乱序、活动错误订阅、上游采集仍运行但本插件已断开、未 live 的健康服务、匿名记录缺失、鉴权失败、房间 closed/error、重复停止/重试、停止部分成功、旧轮询晚到、插件刷新/重启、B 站本地彩排限制、在播下播与断开重叠分别由 AC-01–11 覆盖；工程计划必须确定这些场景的并发与协议实现，不靠 UI 禁用替代服务端约束。

#### 关键实体

- **目标草稿**：尚未提交的平台与对应房间输入；不代表正在接收事件的来源。
- **已保存目标 / 活动目标**：持久化的选择与当前连接归属；连接只能使用已保存目标，活动期间不可切换。
- **本插件订阅**：本插件对单个房间的接收连接；断开不代表上游停止。
- **房间采集**：DyHub 对指定房间的采集活动，可能被其他消费者共享；房间级停止影响这些消费者。
- **本地舞台**：既有角色与声音的输出会话；不等于抖音开播或上游采集服务。

- **SC-04**：正式证据分别标明确定性 fixture、实际安装的鉴权/空态/离线路径和仍未覆盖的真实事件路径；页面与文档不把前两者当作实房间通过。

### 范围外

见 OUT-001；不把独立服务进程合并进插件，也不借 UI 整合重写已发布事件归一化、礼物金额/数量或平台身份规则。

### 假设

主人有现有 Harness 操作权限，独立 DyHub 可按既有部署方式运行。匿名采集仍受网站协议、目标房间和访问限制影响；前次样例证据不能保证本次真实目标可用。服务端兼容细节未分析完前，不预先宣称某个上游操作一定支持安全重试。

### 依赖

- `REQ-002` 已 released；其实际抖音接入、平台隔离与目标锁定为复用基础，新增 Requirement 不重开旧 Feature。
