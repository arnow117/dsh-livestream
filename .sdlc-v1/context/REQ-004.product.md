- 本文是抖音私信互动、登记入口和直播侧资料录入的唯一产品上下文；`confirmed` 记录已确认意图，`open`、接口候选和未核实能力不自动成为已接受实现方案。本轮只记录需求，不授权账号登录、实际收发消息、采集个人资料、模型/TTS/推流/机器人/服务操作或Git提交推送。
- 本需求不修改本仓已released的REQ/FEAT001–003；既有抖音匿名只读输入/本地舞台的边界继续描述其原版本。新增私信是未来增量，不能把旧证据扩写成账号能力通过。

### 需求

#### NEED-001：真实抖音用户与直播 Agent 私聊（confirmed）

- **用户与问题**：观众与直播Agent互动后，需要在同一抖音平台继续私聊并取得登记入口；已有B站 `send_dm` 和抖音只读弹幕输入不能提供这条抖音私聊旅程。
- **期望结果**：直播Agent能在真实获准抖音私聊上下文中接收用户消息并回复正确对象，发送飞书多维表格登记入口，真实反馈发送受理/失败/未知，最终可由测试用户核对收到。
- **用户证据**：用户要求“直播Agent除已有回复TTS+渲染，也可私聊回复用户，发飞书文档登记手机号和人脸照片”，明确首版为“抖音私信（需新增能力）”。本次brief明确保留真实抖音私聊收/回复目标。

#### NEED-002：用户主动登记，机器人直接使用同一资料（confirmed）

- **期望结果**：用户在用途清楚的登记入口主动提交手机号和人脸照片；直播侧通过真实受授权工具/API录入或更新唯一飞书多维表格业务DB，得到可信访客记录关联，供RobotAgent直接查询，不需要机器人连接或联动已开启。
- **用户证据**：“就直接吧飞书多维表格当作db两边一起用，加个skill就好”。两Agent复用同一套Feishu Skill和实际工具；机器人现场消费归qdroid003。

### 约束

#### CON-001：一份共享业务资料，独立于设备（confirmed）

- 两Agent直接读写唯一飞书多维表格业务DB，复用同一Feishu Skill和真实授权工具/API；不建第二访客DB、表格复制同步服务或同步Agent。一个Base内是否分多表、字段/关联及并发接口留后续设计。
- 直播登记不以T1在线、绑定或机器人联动开启为前提；设备离线不能被解释成飞书权限失效。Skill/页面存在不代表API、账号权限、凭据或照片可访问性已具备。
- **来源**：NEED-002及用户确认的两个独立插件/可选联动边界。

#### CON-002：主动提交与可信身份关联（confirmed）

- 私信账号、平台用户/会话、提交人和访客记录需有可核对的可信关联；弹幕昵称、匿名viewer ID、模型参数或人脸相似度不能当作私信授权或访客recordId。不确定时不猜目标、不自动合并他人资料，转可辨的人工确认。
- 登记入口说明接待用途，用户主动提交；手机号/照片不在公开直播TTS、字幕或公开回复里播报，不给观众读取/编辑整表或他人记录的权限。
- **来源**：已确认共享资料/隐私与身份边界；具体入口、权限与关联实现尚未接受。

- **原因**：将平台私聊/直播登记能力放回其插件所有者；迁移产品归属不等于账号能力已开通，也不授权本轮运行。

#### DEC-002：保留抖音目标，不用其他输出抵扣（confirmed）

- 首版目标仍是真实抖音私聊与主动登记；不默认替换成B站、公开评论/弹幕播报、人工代发或本地模拟。若可用实现路径不存在，明确保留受阻步骤并返回选择，不能悄悄降级。
- **来源**：用户已明确选择抖音私信；本次主 Agent 维持该目标并要求核实可行性，没有委托未验证替代路径。

### 用户场景与测试 *(必填)*

以下均为未来验收草案，OPEN-001未解决前不宣称可执行。本轮不制作新UI原型；实际私聊入口和飞书入口待核实，不用模拟点击代替真实账号、收发消息或持久化结果。

#### 用户故事1：正确抖音用户私聊并收到回复（P1）

**为何此优先级**：提供抖音平台内继续交互的独立价值。**独立测试**：在可用路径与实际授权具备后，用自愿测试账号发送私聊，核对Agent收到同一会话、真实回复结果和用户端收到；无需T1或机器人联动。

1. **给定**真实获准账号/工具和可关联私聊会话，**当**测试用户发送消息，**则**直播Agent在正确用户/会话上下文收到，并通过获准工具回复该用户；发送受理、用户实际收到与已读事实分别归因，不由模型自述代替。
2. **给定**接口不支持、账号/用户关系/权限不满足、限额、拒绝、目标不确定或响应未知，**当**尝试处理，**则**显示实际失败/未知及人工下一步，不错发其他用户，不盲重发或改用B站/公开输出抵扣。
3. **给定**重复或迟到消息/发送结果、会话/账号发生变化，**当**回调到达，**则**保留原账号/用户/会话关联，不重复发送，不将旧结果归到新用户或新会话。

#### 用户故事2：私信入口到主动登记、同表可查（P1）

**为何此优先级**：为后续现场接待提供用户主动提交的合法资料。**独立测试**：不连接T1，测试用户收到登记入口后自行提交；真实工具写入唯一共享表并核对其记录及受限访问，机器人侧可通过同Skill/API直接查询同一记录。

1. **给定**故事1的真实私聊及受限登记入口，**当**Agent发送入口、用户实际收到并主动提交接待用途的手机号/照片，**则**共享表中有正确关联、可查询的访客资料；入口已发送与资料已提交分别记录，不依赖机器人在线或联动开启。
2. **给定**无提交、资料缺失/照片不可用、提交人关联不确定、表/照片权限不足或写入失败/未知，**当**处理登记，**则**保留实际不完整/失败状态并给出人工处理，不伪造已登记、不猜合并或覆盖他人记录。
3. **给定**重复提交或登记资料更新与机器人到访/接待回写并发，**当**读写同一业务DB，**则**不重复创建同一提交的业务事实，不以姓名/匿名ID/相似脸猜同一访客；直播资料更新不覆盖有效到访/接待状态，机器人状态更新不覆盖较新资料。具体条件更新/去重方式留工程核实。
4. **给定**公开直播画面/声音和其他观众，**当**登记或反馈结果，**则**手机号/照片不出现在公开TTS/字幕/回复，其他观众不能借入口读取/编辑整表或他人资料；内部诊断也不打印凭据。

#### 用户故事3：将登记成果交给现场接待（P2）

**为何此优先级**：核对跨项目资料可消费，不重复机器人产品。**独立测试**：以同一自愿测试者和真实登记记录，在获得现场授权后引用qdroid003已定义的独立旅程与两仓版本；没有现场条件时只归因登记分项。

1. **给定**故事2的同表记录及qdroid003可用，**当**同一用户到现场，**则**RobotAgent直接查询同一资料并按003完成识别/接待；一个表情确认原到访的语义只执行003，不在直播项目增加第二接待流程或复制DB。
2. **给定**T1离线或现场旅程尚未通过，**当**整理结果，**则**直播私聊/登记仍独立记录其真实结果，组合步骤如实未通过/未运行，不将本地舞台、登记成功或群消息accepted拼成整条接待通过。

#### 边界情况

- 弹幕用户ID/昵称与私聊身份不能自动互换；关联不足时不发送目标消息或标记可靠登记。
- 发送响应丢失先保留未知和原关联，不盲重发；真实接收/发送权限与工具失败分别说明。
- 同一访客资料与每次到访不同；原到访接待规则归qdroid003，直播侧只更新其拥有的登记资料，不回退已确认事实。
- 现有独立直播能力与新私信失败分开；不能因T1未连接而禁止登记，也不能因旧直播released而宣告私信已通过。
